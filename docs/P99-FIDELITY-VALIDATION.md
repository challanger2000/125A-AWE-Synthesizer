# P99 – reproducible EMU8000 audio validation

Status: **measurement infrastructure added; physical 1:1 fidelity OPEN**.

## FSVR methodology, applied without copying GPLv3 code

The independently authored [P99 audit](../tools/p99_fidelity_audit.py) builds upon our **existing** P97/P98 verification instead of replacing working systems.

- **P97** already downloads SHA-pinned original SoundFont Spec Test v3.0 SF2/MIDI + CT4390 FLAC, compiles the current EMU8000 engine in CI, renders 264 s and establishes one shared global level match.
- **P98** already validates MIDI timestamps and controller settings and analyzes 24 Hall/Chorus notes across instrument-level (A), CC91/CC93 (B) and combined (C) sends.
- **P99** separates RMS **level error** from **spectral shape error** (broad-band spectral error with only the median band offset subtracted from the *metric*, never the audio). Very weak reference bands are excluded.
- P99 rejects misleading stereo-width diagnostics for effectively mono/dry physical reference notes (side/mid below −30 dB). Below-threshold signal pairs are excluded from ranking instead of turning analog noise into a reported 40–100 dB acoustic fault.
- P99 compares the **relative send-level trend** with each variant's 0% send as a baseline, without per-note audio scaling. **Only variant B holds the identical note across all send values**. A/C change the actual instrument/sample note and cannot on their own identify a send-gain function.
- P99 stores the SHA-256 hashes of the original MIDI, SF2 and each newly rendered WAV, GitHub commit ID, and native PCM **regression fingerprints** for every effect note: peak, RMS, channel/stereo relationship, spectral centroid, top frequency peaks and 10 ms envelope percentiles. These are for comparing subsequent builds, **not** certification of real hardware fidelity.
- CI uploads JSON and a human-readable Markdown summary. No need for additional full renders beyond the existing P97 one.

## What cannot be borrowed for the historical AWE64 recording

FSVR derives timing offset and recorder clock drift from three short reference-tone markers at both ends of a capture. The original AWE64 Gold v3.0 **analog** recording contains no such known markers. Consequently those alignment and clock-drift corrections **cannot honestly be claimed** for the current experiment. Coarse P97 50-ms RMS envelope alignment and P98 note-time windows remain subject to uncertain capture latency and analog/sample-clock variation.

## New hardware protocol

Request original AWE64 Gold CT4390 **lossless 44.1-kHz S/PDIF**, Creative drivers and exactly matching bank, with **no** effects added after the card, normalization, limiting or resampling. Record a controlled **dry reference** plus separate EQ/filters/ADSR/velocity/pitch and Hall/Chorus sends. For new test sequences, prepend and append explicit marker tones generated by the **same SF2/sample on both hardware and emulator**; save a per-file manifest with sample count, marker times, MIDI/SF2 hashes, controller states, driver/card settings and clock source. Then estimate start/end alignment confidence and fractional clock ratio, rejecting uncertain matches rather than forcing them. The historical v3.0 recording cannot be retroactively furnished with such markers.

**Next unresolved silicon-level issue:** the current 86Box-derived EMU8000 backend runs an explicitly **fitted** reverb/chorus network. New measurements can validate its audio behaviour but cannot extract an undocumented proprietary chip DSP algorithm solely from Creative's effect preset registers.
